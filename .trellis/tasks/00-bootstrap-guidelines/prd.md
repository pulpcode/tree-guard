> 本文件是可供项目负责人审阅的决策记录，不是隐藏提示词。

## 目标

基于当前源码、测试和已经确认的产品边界，建立一套供 Codex 使用的
TreeGuard 开发规范。规范应区分：

1. 不应随 MVP 效果变化的永久安全与可信边界；
2. 为验证可行性而采用的 Shadow MVP 临时限制；
3. 仅用于描述当前仓库现状、不能自动升级为产品政策的事实；
4. 已明确延期、需要在约定时点建立正式任务的工作。

本任务只处理规范、Trellis 工作流与 Codex 适配，不实现 TreeGuard 产品功能。

## 2026-07-28 项目负责人审核决定

以下决定由项目负责人在本轮审核中明确确认，适用范围为本初始化任务及其
形成的规范：

### 永久边界

- 整个外网开发仓库都按外部开发区处理。真实信息树、真实业务文本、内部
  源码、模型请求/响应、内部路径、凭据和可识别身份不得直接外传。
- 节点字段名本身也可能包含业务语义，必须经过严格脱敏并逐字节人工审核后
  才能单向导入外网。只删除 `VALUE`、替换 ID 或使用稳定化名，不构成充分
  脱敏。
- 外网开发只使用经批准的 Schema 形状、固定枚举/错误码、聚合统计和完全
  虚构样例。无法确认来源或敏感性时必须停止并请求安全替代材料。
- 从受保护环境调用 Web、MCP 或其他外部工具前，必须先审查并脱敏查询文本；
  不能把受保护事实先发给工具、再只约束其落盘结果。
- LLM 输出始终是待审建议，不能成为事实来源或最终裁决。可回放的确定性检查、
  来源证据和人工裁决共同构成可信边界。
- `bobot` 仅作为不对应真实人员的开发/代理别名。禁止落盘的是受保护环境中
  的真实身份或可反向识别身份。

### Shadow MVP 临时限制

- 首期产品能力采用旁路运行：读取批准的快照，生成建议、证据和审查记录到
  sidecar/overlay 工件，不修改生产 MongoDB、生产信息树或业务版本。
- “无生产写入”“不自动应用 Patch”等是 MVP 风险控制，不是永久产品结论。
  在最小可行性验证后，根据准确性、专家采纳率、误报、审查成本和可回放性
  决定是否保留或逐步放开。
- 初期优先治理一部分有代表性的子树，并以正式 `version` 快照为单位；暂不
  依赖未开放接口的 MongoDB 中间保存副本。
- 初期不把 embedding 模型设为必需依赖。只有当候选召回质量或规模验证表明
  确有必要时再引入。

### 当前仓库事实

- 当前没有日志框架；已有 CLI 以版本化 JSON 和退出码输出汇总结果。规范应
  准确描述现状，不能把计划中的可观测性能力写成已实现。
- 当前没有数据库驱动、ORM、迁移层或生产 Patch 写入器。保留
  `persistence-and-integration.md`，用于说明文件、环境变量、Provider 和
  网络边界，而不是虚构数据库架构。
- 当前存在跨模块导入下划线私有 helper 的技术债。下一次真实复用时再提取
  公共模块，不在本规范任务中做无需求支撑的全量重构。
- 当前未配置 Ruff、mypy、coverage 门禁、pre-commit 或 CI。检查结果必须
  如实写“未配置”，不能写成“已通过”。

### Codex 与审查权限

- 当前只保留 Codex，暂不维护 Claude Code 与 OpenCode 适配器。
- `.trellis/scripts/` 和 `trellis-meta` 中可保留上游 Trellis 的通用平台枚举与
  维护参考；它们不是本项目已配置/支持的平台。为“形式上只出现 Codex”而删改
  上游通用 runtime 会制造不必要的升级分叉。
- Codex 默认由主代理内联执行；只有任务边界清晰且文件所有权不重叠时，才
  并发委派子任务。
- 开发阶段的 `trellis-check` 代理可以在外网开发仓库内修改本任务范围代码、
  运行 Bash 和测试，以修复审核发现；它不得访问或修改生产环境、生产数据
  或受保护源码。
- 产品运行时的 AI 审查结果只进入旁路工件。开发代理“可自修代码”与产品
  “不可修改生产信息树”是两个不同层面的权限，不得混为一谈。
- Codex 不读取任务 JSONL 中声明的任意文件路径。上下文只从当前任务 PRD、
  固定 spec index、适用规范和当前任务的 `research/` 目录按需选择。
- Trellis 兼容命令仍保留 JSONL 校验，但只允许 `.trellis/spec/` 或当前任务
  `research/` 下的 realpath；拒绝绝对路径、`..`、其他任务、代码路径、
  archive task 和 symlink escape。Codex inline 新任务不再 seed JSONL。

## 延期事项与建立任务的时点

以下事项不能埋在初始化任务中假装完成：

1. **结构化诊断导出**：设计“内网结构化事件 → 正向允许列表导出器 →
   人工审核 → 单向外网诊断包”。原始日志文件直接外传不是批准方案。
2. **`ai.called` 状态缺陷**：模型调用成功但内部输出写入失败时，当前实现
   可能错误报告 `ai.called=false`。这是独立产品缺陷。
3. **工程质量基线**：Ruff、mypy、coverage、pre-commit 和 CI 在 Shadow MVP
   最小可行性验证完成后，根据实际维护成本建立任务。
4. **面试展示材料**：最小可行性验证后，补充架构图、指标、可回放案例、
   失败分析与演示脚本，不能用尚未验证的效果包装项目。

第 1、2 项在本初始化任务完成审核并提交后建立正式 Trellis 任务；第 3、4 项
在 Shadow MVP 可行性结论形成后建立。随后立即建立并推进
“AI 辅助信息树子树治理 Shadow MVP”主产品任务。

## 编写原则

1. 优先从源码、测试和现有约定提取规则，并引用真实仓库相对路径。
2. 当前事实必须标注为当前事实；MVP 约束必须写明复审触发条件。
3. 永久边界只能来自已确认的安全、可信或合同要求。
4. 不把愿景写成已实现能力，不用虚构的“最佳实践”覆盖现有代码。
5. 新增的项目规范、任务说明和工作日志优先使用中文；命令、协议字段、代码
   标识及已有清晰英文无需为了形式统一而改写。

## 完成与提交顺序

1. 运行 Trellis/Codex 配置静态检查和当前产品测试。
2. 审阅所有待提交路径，确认没有凭据、真实数据、受保护字段名或内部路径。
3. 提交初始化工作。
4. 使用无自动 Git 操作的命令归档：

   ```bash
   python3 ./.trellis/scripts/task.py archive 00-bootstrap-guidelines --no-commit
   git status --short
   ```

5. 单独审阅并提交归档与最小化中文日志。
6. 建立延期事项任务和 Shadow MVP 主产品任务，开始下一阶段。
