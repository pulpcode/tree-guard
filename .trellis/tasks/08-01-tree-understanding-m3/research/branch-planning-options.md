# M3 结构变更测试场景规划研究

## 问题与范围

- 日期：2026-08-02；
- 问题：当前信息树通常只有 Schema 结构、没有实例值，如何让信息树理解 Agent
  可靠地准备自然语言结构建模/变更测试候选；
- 范围：只研究本外网仓库已有合同和完全虚构实验的聚合结果，不使用受保护数据、
  外部查询、Prompt、模型请求/响应或原始日志。

## 仓库依据

- `src/treeguard/tree_understanding.py` 已提供完整树画像、一级分支画像、有界模型
  投影、临时引用和可信来源回放；
- `src/treeguard/change_intent.py` 的请求包含 requirement、可选父节点和
  kind/value type/cardinality hints；
- `src/treeguard/retrieval.py` 与 `src/treeguard/semantic_recommendation.py` 采用
  “确定性筛选/排序 → 有界模型投影 → 本地来源绑定”的分层模式；
- `src/treeguard/workbench_validation.py` 的 `ValidationScenarioOracle` 只记录
  可观察状态，不是语义 Gold；
- 当前青岚运行时适配器明确只比较意图阶段状态；
- 父任务完全虚构实验显示：模型能概括主要业务区域并生成自然语言，但自由生成
  会遗漏分支、跨分支组合并遗漏部分诉求证据；明确分支后归属改善。

## 修正后的共同约束

1. 生成对象是信息树结构建模/变更需求，不是实例事实查询；
2. 规划器拥有覆盖、风险族、锚点、顺序、预算和阶段目标；模型不能决定 Oracle；
3. 单分支模式用于清晰正向场景，但同名、错误父节点和跨分支冲突需要规划器明确
   允许的有界对照模式；
4. finding 质量结论与测试场景生成保持不同语义，但机械 finding 可以作为只读
   挑战锚点；
5. 候选保持待人工审核、非 Gold、非 Patch，不直接进入验证数据集；
6. 候选合同面向意图、召回和推荐，首个运行切片只比较意图状态；
7. 单次投影临时引用不能跨投影充当稳定身份；
8. 真实树只进入受保护环境内网模型，外网自动化只使用完全虚构 transport。

## 规划方案

### A. 确定性稀疏能力矩阵（推荐）

- 每个预算内一级分支至少一个 branch-local 候选；
- 每个存在确定性锚点的核心风险族至少一个全局挑战候选；
- challenge 单元按需要使用 branch-local、contrast 或 ambiguity 模式；
- 不对全部分支和风险族做笛卡尔积；
- 分别报告分支、风险族、目标阶段和节点投影覆盖。

优点：直接针对当前 MVP 的意图、召回、复用、放置、消歧和拒绝能力，调用量可控，
并能防止自由生成遗漏覆盖目标。

限制：不能声称每个节点都被语义理解；自然语言与结构证据是否真正一致仍需审核。

### B. 全节点递归分块

- 递归划分所有大分支，直到每个节点至少进入一次投影；
- 每个分块再生成候选并做归并、去重和覆盖矩阵。

优点：可以证明所有节点都获得过模型输入机会。

限制：节点被看到不等于产生有效测试，调用、重复、失败恢复和审核成本显著更高，
不优先解决当前已观测的测试能力覆盖问题。

### C. LLM 自主选择后过滤

- 让模型选择重点分支、风险类型和候选，再由本地过滤。

优点：可能发现规划器没有定义的自由探索问题。

限制：实验已经证明自主覆盖和跨分支稳定性不足；过滤不能补回遗漏，模型自选风险
又会形成生成者兼任计划者的问题，因此不能作为覆盖主线。

## 分阶段边界

- 候选字段从一开始兼容当前 MVP 请求形状并声明目标阶段；
- M3 首个运行切片只比较意图 draft status；
- 召回候选和推荐动作在后续切片单独建立可观察 Oracle，不把未运行状态算通过；
- 人工审核负责冻结预期，生成模型不能输出或批准 Oracle。

## 核心风险集与规模观察

- 首切片确认采用 8 类：已有节点复用、新节点放置、同名澄清、错误父节点/跨分支、
  kind 冲突、cardinality 冲突、证据不足和无界组合拒绝；
- 48、312、2,001 节点完全虚构树分别有 4、6、6 个一级分支；
- 2,001 节点树有 82 条机械 finding，但挑战计划按风险族选有界锚点，不按 finding
  数量线性增加调用；
- 按每个预算内一级分支一个基础单元、每个适用核心风险族最多一个全局挑战单元，
  三档预计分别不超过 12、14、14 个计划单元；
- 已确认单次运行默认最多 16 个计划单元、公开硬上限为 32；每个单元最多生成一个
  接受候选并允许 Provider 重试一次，因此默认/硬上限下最坏分别为 32/64 次模型
  HTTP 调用；
- 超预算目标必须按确定性优先级明确记为遗漏并使批次保持 `PARTIAL`，不能用截断后
  的结果声称覆盖完成；
- 已确认部分单元失败不使成功候选作废：成功候选仍可独立进入人工审核，批次保持
  `PARTIAL` 并披露失败/遗漏；全部执行单元失败时没有可审核候选；
- 已确认采用均衡预留：最多为 8 个适用核心风险族各保留一个单元，其余名额用于
  一级分支基础覆盖；不适用的风险名额归还分支覆盖；
- 上述数字只用于外网虚构数据设计，不外推真实生产分支分布或调用成本。

## 结论与限制

- 采用 A 作为 M3 主路径，B 作为后续大树递归扩展，C 只作为覆盖完成后的补充；
- 覆盖成功应由“分支 + 适用风险族 + 已执行阶段”定义，节点投影覆盖只作披露；
- 现有 `TopLevelBranchProfile` 只提供节点数、相对深度和最大直接子节点数，且合同中
  的 `(root_node_id, branch_node_id)` 排序只用于规范化与复现，不具有业务优先级；
- 已确认一级分支超过剩余名额时采用结构代表性：按固定顺序先选节点数最大、相对
  深度最大、直接子节点数最大的分支并去重，再按规范化结构向量差异补足；内部 ID
  只作同分决胜，不表达业务重要性；
- 候选与执行之间需要显式可信审核门：生成模型不能自动冻结请求或 Oracle；M3 只
  允许已审核的内存场景进入意图阶段，且不注册数据集 Provider；
- M3 产品与失败边界已收敛，可以进入实现计划确认；
- 本研究不保存模型文本、Prompt、请求、响应 envelope 或真实业务材料。
