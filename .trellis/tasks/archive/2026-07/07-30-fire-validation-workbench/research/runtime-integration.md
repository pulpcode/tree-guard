# 消防验证数据与工作台接入研究

## 问题

如何在不复制治理策略、不扩大浏览器数据边界的前提下，把消防虚构场景接入现有
Web 治理闭环，并区分冻结合同 oracle 与真实模型运行结果？

## 范围

- 日期：2026-07-30。
- 仅检查本仓库现有 Workbench、Governance Service、Simulator、前端 API 和消防
  虚构数据合同。
- 不访问生产接口、真实信息树、凭据或外部服务。

## 仓库相对依据

- `src/treeguard/web.py`：当前 API 由可信 Repository 和 Governance Service
  组成，治理 case 只接受资源、版本和有界需求提示。
- `src/treeguard/workbench_governance.py`：现有流程已具备 operation、一次澄清、
  候选召回、语义建议、人工复核、sidecar 和内存诊断。
- `src/treeguard/simulator.py`：当前模拟仓库只暴露一个虚构资源；模型仿真响应由
  simulator 场景控制，不读取消防场景中的冻结模型输出。
- `src/treeguard/fictional_fire_data.py`：三档树和场景可以确定性生成，场景包含
  请求提示、冻结模型输出、人工动作和合同 oracle。
- `web/src/GovernancePanel.tsx`、`web/src/api.ts`：前端已经有单 case 状态机、
  operation 轮询、模型模式和诊断展示，不需要重写治理页面。

## 结论

1. 消防树应通过可信只读 Repository 边界进入现有 Workbench，避免浏览器上传树
   或让治理服务直接读取任意文件路径。
2. 场景目录 API 只返回安全投影：档位、场景引用、用途、需求提示、可选父节点
   临时引用和非 Gold 限制；稳定节点 ID 与冻结模型输出留在服务端。
3. 单场景真实运行应复用现有 Governance Service。新增层只负责选择场景、创建
   受限 case 和对照合同，不重新实现意图、召回或语义规则。
4. 冻结模型输出适合确定性测试和合同基线，不等于新的模型调用。真实百炼结果
   必须单独标记为 live run，并继续使用显式出域批准。
5. 当前 operation registry 只有单进程线程池，没有批量队列、恢复或成本预算。
   首个切片若直接做批量，会同时引入调度、限流、自动人工动作和聚合语义问题。

## 可行方案

### A. 单场景预设叠加现有治理闭环（推荐）

- 模拟仓库新增三档消防虚构资源。
- 新增安全的场景目录/详情投影，选择场景后预填现有治理表单。
- 运行继续走现有 case API；后端提供只读合同对照结果。
- 改动边界最小，可先证明真实模型、候选和人工复核链路。

### B. 首期直接增加批量验证任务

- 新建 batch registry，自动执行场景、澄清和审查动作，再聚合报告。
- 能快速得到一组结果，但会引入调用成本、并发、失败恢复和“自动动作不是专家”
  的产品语义。

### C. 增加消防冻结输出回放模式

- Web 直接回放数据集内冻结模型输出，得到完全确定性演示。
- 稳定且便宜，但主要重复现有测试，不能证明当前百炼模型的实际产出能力。

## 限制

- 现有 oracle 不是专家 Gold，合同对照只能说明流程和预期候选是否一致。
- 真实模型建议仍需人工审查；首个切片不能产生生产准确率或自动 Patch 结论。
- 批量运行、跨进程恢复和内网 Qwen 留待独立后续切片。
