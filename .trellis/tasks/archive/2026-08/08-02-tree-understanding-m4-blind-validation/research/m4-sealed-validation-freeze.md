# M4.5 新未见数据密封验证冻结候选

## 目的

fire M4 Silver 已用于 Prompt 校准并暴露语义失败模式，不能继续承担泛化或
`GO_SHADOW` 门控。本候选定义下一轮新数据生成前必须冻结的实现、数据隔离、执行和
评分边界；不包含场景正文、树节点、模型请求、响应或隐藏 Oracle。

## 冻结对象

- 功能基线：当前功能分支获批提交；未提交工作树或浮动分支名不能作为数据绑定；
- Intent：`treeguard.change-intent.zh.v4`；
- Semantic：`treeguard.semantic-recommendation.zh.v3`，首次本地合同失败时只允许携带
  固定 `SEMANTIC_*` 错误码完整重试一次；
- 模型：冻结实际 Provider、模型名、endpoint 类别和生成参数；默认候选模型为
  `qwen3.6-35b-a3b`，执行前必须把实际值写入私有运行 manifest；
- 运行合同：当前 capability overlay、request-aware preflight、确定性召回、结构冲突
  门禁、稳定目标映射和公开聚合报告；
- 评分合同：打开密封数据前冻结本页的分母、阈值与停线规则。数据打开后不得修改
  Prompt、模型、重试政策、比较器或 Oracle；若修改，当前数据立即降级为校准集。

## 数据隔离与规模

- 数据必须由独立 worktree/对话生成；本功能对话只接收 dataset identity、来源类别、
  规模、覆盖计数和 digest，不读取树、场景或 Oracle 正文；
- 使用一棵全新、同领域、clean-room、完全虚构且未进入任何既往模型请求的树；不得从
  fire M4 或青岚树复制、改名、同义改写或笛卡尔积扩张；
- 树目标规模为 800–2,000 个节点，允许因语义设计在区间内自然收敛。超过 2,000 不因
  本轮验收额外加分；本轮不准备 10,000–50,000 节点压力树；
- 正式执行集固定 24 条，目标组成是 18 条 `PROCEED` 完整链路与 6 条 `CLARIFY`
  短路。澄清必须由请求自身的互斥解释、范围或组合歧义支持，不得依靠制造坏树；
- 若独立审核认定某条澄清不成立，该条不得改标签充数，只能由预先准备的同类别密封
  余量替换。所有替换必须发生在功能侧看到正文之前，并重新冻结整个执行集 digest；
- 完整链路至少覆盖普通唯一目标、多可接受目标、hard negative、Top-K 边界、跨分支、
  kind 冲突、cardinality 冲突和显式空目标；不要求对风险维度做笛卡尔积。

## Oracle 与审核

- Oracle 在首次模型调用前由独立人工审核冻结；Codex 可辅助形成 Silver 候选，但不能
  把自身候选自动升级为 Gold；
- 每条场景冻结 request-observable Intent profile、预期路径、召回可接受稳定目标集、
  Top-K、推荐动作—目标—关系联合集合及适用性；
- Oracle 不包含模型 rationale，不使用运行时临时候选编号，不把无法从 request 或树
  确定支持的自由文本作为精确 Gold；
- 数据、场景、Oracle、审核包、功能提交和运行 manifest 分别计算 digest，并在执行前
  做闭包校验；任一字节漂移均停线。

## 三次重复性执行

- 24 条场景在相同冻结配置下各运行 3 次，共 72 个 Intent 观测单元；
- `CLARIFY` 按合同短路；`PROCEED` 仅在 Intent 匹配后进入确定性召回，仅在召回命中后
  进入 Semantic；上游失败不重复记为下游错误；
- 每次模型调用仍保持单阶段最多两次尝试；分别报告首发合同合法率和重试后最终合法率，
  不用“最好一次”代替重复性；
- 公开报告只含固定状态、固定错误码和聚合计数。原始 Prompt、请求、响应和隐藏 Oracle
  只允许出现在 `0600` 私有临时工件中，实验结束按既有数据边界处理。

## 推荐门槛

以下门槛在数据正文生成前冻结，避免看结果改分数线：

1. 来源、密封、digest、执行资格、记账或隐藏参照泄漏为零失败；任一失败直接
   `NO_GO`；
2. Intent 与 Semantic 的重试后最终合同合法率分别不低于 98%；同时报告首发合法率，
   但首发合法率只作成本和稳定性诊断；
3. `PROCEED` 且 Intent 匹配的场景，确定性召回 Top-K 命中率必须为 100%；
4. Intent Oracle 匹配率、适用 Semantic Oracle 匹配率和端到端 Oracle 匹配率分别按
   每轮报告；三轮中任一轮端到端不得低于 75%；
5. 至少 18/24 场景达到三次全部端到端匹配；三次结果发生变化的场景单列为不稳定，
   不能用多数票隐藏；
6. 澄清单独报告 precision、recall 和 3/3 稳定数；不得把“问题非空”当作澄清正确；
7. 对 kind、cardinality 或跨分支硬冲突，不允许产生被本地结构门禁接受的错误复用；
   出现一次即 `NO_GO`。

通过只表示当前模型和工程链路值得进入有人工监督、只读、可回退的受保护环境 Shadow
验证，不表示达到生产准确率、Gold 自动化或自主修改信息树。

## 停线与污染规则

- 数据团队若需要改变运行时 Schema、Prompt 或比较器，停止造数并回到功能合同；
- 功能团队一旦看到场景、树或 Oracle 正文，只能执行已冻结方案，不能再修改实现；
- 首次揭盲后，无论通过或失败，该数据都转为回归/校准资产；下一次正式门控必须使用
  新密封数据；
- 本轮失败先按 Intent 合同、Intent 语义、确定性召回、Semantic 合同、Semantic 语义、
  Oracle/实验设计六类归因，再决定换模型、拆小任务或调整产品边界。

## 启动顺序

1. 审阅并提交当前功能基线，取得不可变 commit；
2. 数据 worktree 从该 commit 创建新任务，只接收本页聚合合同；
3. 数据侧完成 Charter、覆盖蓝图和 Oracle Schema 审核，功能侧不看正文；
4. 数据侧生成、人工审核并冻结 24 条执行集和余量，交付 digest 与聚合 preflight；
5. 功能侧验证闭包并冻结实际 Provider/模型/endpoint/参数；
6. 执行三轮，揭盲评分，输出聚合报告与失败归因；
7. 根据门槛决定 `GO_SHADOW` 或 `NO_GO`，不在同一数据上继续调参后重新门控。
