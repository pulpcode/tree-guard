# M4 完整能力验证合同方案

## 问题与范围

- 日期：2026-08-02；
- 目标：在不破坏上一里程碑来源绑定与序列化合同的前提下，增加意图、召回和推荐的
  完整能力 Oracle、分阶段结果与 Shadow 可行性门槛；
- 依据仅来自仓库现有公开代码合同和完全虚构聚合设计，不包含模型流量、隐藏场景、
  Oracle 正文或受保护数据。

## 仓库现状

- `workbench_validation.py` 已能从可信 Provider 执行治理流程，但只比较可观察状态；
- `scenario_validation.py` 已有候选、批次、投影、树快照和人工审核的传递绑定，但执行
  合同固定为意图首切片；
- `retrieval.py` 的候选包含稳定节点身份与排名，可直接支持内部 Top-K 判断；
- `semantic_recommendation.py` 使用运行级候选引用，必须通过同次候选集映射回稳定节点
  身份后，才能与长期 Oracle 比较动作、目标和关系。

## 可行方案

### A. 在已审核场景上增加来源绑定能力 overlay（推荐）

- 保持上一里程碑 action、record 和 intent-run v1 不变；
- 新增独立能力 Oracle/review/run/batch-report 版本，overlay 绑定已有 reviewed hash、
  树快照、计划和受审字节；
- 运行器复用现有意图、确定性召回和推荐 Provider，内部完成临时引用到稳定身份映射；
- 公开报告只输出阶段状态、固定 code、分母和聚合门槛。

优点：兼容旧回归，来源链清晰，最符合数据 sidecar 所有权。代价：新增一组显式版本
和序列化合同。

### B. 直接扩展 Validation Workbench 的状态 Oracle

- 在现有 Provider 场景和 comparison 中加入目标与推荐字段。

优点：复用现有 Web 执行入口。缺点：生成候选的人工来源绑定较弱，容易把正式 Provider
fixture 与尚未晋升的盲测 sidecar 混在一起，并扩大既有 API 兼容面。

### C. 运行后由外部评审器判断

- 保留现有执行，只把输出交给另一个模型或独立脚本评分。

优点：改动少。缺点：不能提供确定性目标身份、合同重放和失败关闭；外部模型判断也不能
成为 Gold 或 go/no-go 的唯一依据。

## 结论

采用 A。完整能力 overlay 是新版本合同，不修改上一里程碑 v1；状态/安全硬失败与语义
偏差分别记账。意图不匹配或召回目标未命中时，后续阶段以固定上游短路状态结束，避免
把同一根因重复计算为多个语义失败。外部强模型可以日后作为非权威 Critic，但不进入
首轮门槛。

## 限制

- 首轮不增加 UI、数据库、队列或新依赖；
- 不在公开报告中包含请求正文、稳定节点身份、Oracle 集合、模型文本或 trace；
- 数据 sidecar 只有在功能合同提交冻结后才能物化。
