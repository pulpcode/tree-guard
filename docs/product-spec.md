# TreeGuard 产品规格

状态：设计基线
日期：2026-07-27
阶段：文件型 Shadow MVP

## 1. 背景

信息树是一种树形领域 Schema，由递归的 `CONCEPT`、`PROPERTY` 和 `VALUE` 节点组成：

- `CONCEPT` 组织业务语境；
- `PROPERTY` 声明待采集或抽取字段、数据类型和基数；
- `VALUE` 承载具体文档或业务实例中的运行时数据。

上述三类是领域概念。当前实际导出 JSON 的拓扑节点只观察到 `concept/property`；实例 VALUE 以内嵌 `value` 对象挂在属性旁边，而不是 `node_type=value` 的拓扑节点。TreeGuard 的治理快照默认只导入 Schema，VALUE 不进入索引、Prompt、Trace 或 Schema 哈希。

信息树既是“树形数据模板”，也是不同软件之间的 Schema Contract。现有 Spring Boot + MongoDB 信息树仓库负责主题信息树的存储、管理和版本控制，下游软件从仓库获取树并生成或消费结构化数据。

典型下游是定制邮件：邮件模板由自然文本和绑定到具体 `node_id` 的输入组件组成。填写后生成树形 JSON，并在系统中流转。

实际信息树经常超过 2,000 个节点。随着长期手工迭代，建设人员很难掌握全局语义，容易形成：

- 同义或近义节点重复建设；
- 相同名称表达不同语义；
- 字段挂载位置不一致；
- 通用信息和场景信息混杂；
- 特殊任务复制整套公共结构；
- 修改时无法完整识别下游依赖；
- 版本记录存在，但变更原因通常只有几个字或一句话。

## 2. 产品目标

TreeGuard 应帮助建设人员回答以下问题：

1. 当前需求描述的业务主体、角色、场景和生命周期是什么？
2. 整棵信息树中是否已经存在可直接使用的节点？
3. 是否存在可复用的语义合同，但仍需在当前路径新增物理节点？
4. 特殊字段属于长期主体属性、本次任务参与状态，还是任务整体属性？
5. 当前需求是否与已有节点重复、冲突或存在稳定的上下文扩展关系？
6. 如果专家暂时不能确定，应保存哪些思考、假设和证据缺口？
7. 建议形成 Patch 后，会影响哪些已知下游消费者？
8. 这次建议是否可以完整回放，并与独立人工结论进行对比？

## 3. 非目标

MVP 不解决：

- 自动生成完整的 2,000+ 节点信息树；
- 从任意自然文本中完成通用结构化抽取；
- 自动发布或直接修改生产 MongoDB；
- 自动删除、移动、合并已有节点；
- 自动修改已有字段类型、基数或语义；
- 自动替代领域专家进行最终裁决；
- 通过模型微调解决所有领域问题；
- 通过 AI 合成数据证明真实消防业务准确率。

## 4. 核心用户与职责

### 4.1 信息树建设人员

主要操作者，负责：

- 提交新增需求和拟挂载位置；
- 确认或修订变更意图卡；
- 检查候选节点、结构、类型和基数；
- 审查声明式 Patch；
- 在未来生产阶段执行发布。

### 4.2 领域专家

语义权威，负责：

- 判断业务主体、角色、适用场景和边界；
- 提交确定结论或自由形式的思考；
- 指明未知事实、风险和待取证项；
- 审批或拒绝 Semantic Overlay 中的语义结论。

### 4.3 版本发布负责人

检查权限、影响和版本条件。MVP 可以由信息树建设人员兼任，但 Trace 必须分别记录角色。

邮件填写人员和普通业务用户不是 MVP 的直接用户。

## 5. 初始化流程

1. 内网以文件形式导入当前完整信息树及至少两个历史版本。
2. 确定性代码依据 `node_id` 重建新增、修改、删除和疑似移动血缘。
3. 将一次版本中不同子树的修改拆成原子变更簇，版本只是容器，不直接作为一个样本。
4. 为整棵树建立名称、别名、路径、结构和向量索引。
5. 选择一棵消防领域高价值子树作为首个治理范围，但候选查重仍覆盖整棵树。
6. AI 为试点节点起草公共语义合同、差异和疑似问题，专家分组审批 Semantic Overlay。
7. 从真实历史变更簇和新采集需求中建立至少 30 条专家独立裁决的冻结评测集。

历史版本只作为弱证据。粗糙的历史操作不能自动视为正确先验。

## 6. 在线 Shadow 流程

1. 建设人员在拟挂载位置进入“AI 建模建议 / 新增审查”。
2. 用户用自然语言说明新增需求，拟挂载位置作为提示传入。
3. AI 编译结构化变更意图卡。
4. 用户确认或修订意图卡；缺少关键事实时只追问一个最重要问题。
5. 系统在全树执行宽召回和局部精排。
6. AI 比较前 5–8 个候选，输出明确建议、关键追问、`NEED_EVIDENCE` 或 `ABSTAIN`。
7. 专家可以提交自由思考，系统保留原文并整理为事实、假设、分歧、风险和待取证项。
8. 只有 `APPROVED` 的结构化语义结论才能进入 Patch 阶段。
9. 系统生成带基础版本、节点哈希和幂等键的声明式 Patch。
10. 确定性代码进行结构校验、Dry Run 和已知下游影响分析。
11. 领域专家审批语义，建设人员审批结构。
12. Shadow 阶段冻结 AI 建议，与先独立完成的人工作答进行比较，不写生产库。
13. 全流程保存 Trace，用于错误归因、模型对照和回放。

## 7. 关键交互

### 7.1 变更意图卡

至少包含：

- 业务主体；
- 数据或人员角色；
- 适用任务类型；
- 生命周期；
- 长期主体属性、本次任务参与状态或任务整体属性；
- 数据类型；
- 基数；
- 拟挂载位置；
- 用户原始需求；
- 已确认事实；
- 尚未确认的假设；
- 需要补充的关键证据。

### 7.2 候选比较页

不能只显示相似度分数，必须比较：

- 节点完整路径；
- 主体与角色；
- 适用场景和排除场景；
- 数据类型和基数；
- 公共字段和场景字段；
- 已审批的语义定义；
- 与其他节点的语义关系；
- 已知下游引用；
- 推荐理由和排除理由。

用户选择的父节点只能提高局部候选权重，不能限制全树查重。

### 7.3 专家讨论记录

讨论状态固定为：

```text
OPEN
→ DELIBERATING
→ NEED_EVIDENCE
→ PROVISIONAL
→ APPROVED / REJECTED
```

系统必须同时保存：

- 专家原始表述；
- AI 整理后的结构化内容；
- 每次修订；
- 引用的证据；
- 审批人和审批时间。

`PROVISIONAL` 和 `NEED_EVIDENCE` 不进入生产可用 Overlay，也不能生成可发布 Patch。

### 7.4 Patch 与影响预览

必须展示：

- 基础树版本和快照哈希；
- 具体操作及目标路径；
- 新增、直接使用和合同复用内容；
- 节点级前置条件；
- Dry Run 结果；
- 邮件模板的已知影响；
- Usage Manifest 的同步时间和覆盖范围；
- 过期、未知或不完整风险。

界面不得笼统显示“无影响”。MVP 应显示：

```text
已知影响范围：邮件模板
其他消费者：未知
Usage Manifest 最近同步时间：……
```

### 7.5 Trace 回放

回放必须能回答错误发生在：

- 意图理解；
- 候选召回；
- 候选排序；
- 语义比较；
- 风险放行；
- 人工修订；
- Patch 编译；
- 结构验证；
- 影响分析；
- 发布执行。

“Trace 回放”使用当时保存的模型输出，确定性重跑后续步骤。“模型重跑”则使用冻结输入调用新模型或新 Prompt，结果不要求逐字一致。

## 8. 语义动作模型

基础信息树是严格单父节点结构，因此必须区分物理节点复用和语义合同复用。

| 动作 | 产品含义 | Patch 行为 |
|---|---|---|
| `USE_EXISTING_NODE` | 当前业务可直接使用已有节点 | 不修改基础树 |
| `ADD_NODE_FROM_CONTRACT` | 当前路径需要物理节点，但语义合同已存在 | 新增普通物理节点并记录合同关系 |
| `ADD_CONTEXT_FIELD` | 为稳定特殊场景增加字段 | 在当前子树新增 `PROPERTY` 或必要容器 |
| `ADD_ALIAS_OVERLAY` | 名称或别名问题，不应新增基础节点 | 只更新 Overlay 草稿 |
| `NEED_CLARIFICATION` | 缺少一个关键事实 | 返回追问，不生成 Patch |
| `NEED_EVIDENCE` | 专家需要继续调查 | 创建讨论记录，不生成 Patch |
| `ABSTAIN` | 系统无法可靠判断 | 转人工，不生成 Patch |

删除、移动、合并、改类型和改基数只能产生 `PLAN_ONLY` 风险说明，不进入 MVP 的可执行动作集合。

## 9. 人员信息的建模原则

“人员”不是完整语义。至少还需要：

- 人员在业务中的角色或关系；
- 适用任务；
- 生命周期；
- 字段属于长期属性还是本次任务状态；
- 类型与基数约束。

建议使用三层语义：

1. `PersonCore`：姓名、证件等长期主体属性；
2. `TaskParticipantBase`：角色、参与状态等本次任务关系；
3. `<TaskType>ParticipantExtension`：稳定存在的特殊任务字段。

例如某类特殊任务中的“资质等级”和“暴露时长”：

- 资质等级需要判断是长期人员资质，还是本次任务采用的资质状态；
- 暴露时长更可能属于本次任务参与状态；
- 不应默认在特殊任务下复制完整人员子树；
- 也不应把全部特殊字段堆进一个全局人员节点。

Overlay 可以保存 `SAME_AS`、`SPECIALIZES`、`DISTINCT_FROM`、`REUSES_CONTRACT` 和 `OVERLAPS_WITH`，但物理 Patch 必须展开成现有系统可以理解的普通节点。

## 10. MVP 功能范围

P0：

- 文件型当前树和历史版本导入；
- 基于 `node_id` 的血缘与 Diff；
- 全树混合召回和局部精排；
- 自然语言变更意图卡；
- 选择性语义建议和拒答；
- Semantic Overlay；
- Deliberation Record；
- 非破坏性声明式 Patch；
- Dry Run 和版本前置条件；
- 文件型邮件 Usage Manifest；
- Trace、回放和冻结评测；
- 本地 Qwen 接入；
- 至少 30 条真实专家 Gold；
- 虚构合成数据和契约测试。

P1：

- 自动公共语义合同聚类；
- 更复杂的历史共同变更分析；
- 多模型 Proposer/Critic；
- 多消费者影响分析；
- Spring Boot 只读 API Adapter；
- 待审批 Patch 接口。

P2：

- 正式发布集成；
- 迁移计划辅助；
- 在积累至少 300 条稳定专家案例后评估微调；
- 将治理结果反哺自然文本抽取。

## 11. 面试演示脚本

演示使用明确标注的虚构或严格脱敏案例。

输入：

> 某类稳定特殊任务的参与人员需要记录资质等级和暴露时长。

演示步骤：

1. 意图卡识别人员角色、特殊任务场景、多人基数和未确认假设。
2. 全树找到通用任务参与人员、既有人员资质定义及另一子树中的近义结构。
3. AI 追问资质等级属于长期资质还是本次任务实际状态。
4. 专家不必立即分类，可以提交完整思考。
5. AI 将思考整理成两种假设、风险和待取证项。
6. 专家确认后，系统建议使用通用参与人员合同，只新增特殊任务扩展字段。
7. Patch 预览展示新增物理节点、语义合同关系、基础版本和已知邮件影响。
8. Shadow 阶段只冻结建议，不发布。
9. 展示完整 Trace。
10. 再演示一个证据不足案例，由系统正确 `ABSTAIN`。

该故事同时体现业务价值、LLM 语义能力、混合检索、Schema 编译、Human-in-the-loop、风险门、跨系统影响分析和可回放工程能力。
